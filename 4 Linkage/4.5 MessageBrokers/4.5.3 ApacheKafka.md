# Apache Kafka как брокер сообщений

Apache Kafka, как мы с вами уже знаем, — это брокер событий, который помогает передавать события от "главного героя" к "зрителям". Kafka делает обработку быстрее, изолируя тяжёлые задачи и обеспечивая высокую надёжность.



# Kafka vs RabbitMQ

Прежде чем сравнивать, зафиксируем главное: Kafka и RabbitMQ решают одну задачу (передать сообщение от A к B), но построены вокруг разных идей. Kafka — это **лог**, в который пишут и из которого читают. RabbitMQ — это **брокер**, который решает, кому и как доставить сообщение. Почти все различия в таблицах ниже выводятся из этого одного факта.

---

## Две модели — две схемы

**RabbitMQ: брокер решает за вас**

```text
Producer ──► Exchange ──(binding + routing key)──► Queue A ──► Consumer 1
                  │                                        └──► Consumer 2
                  └──(binding)──► Queue B ──► Consumer 3
                       ↑
              сообщение удаляется после ack
```

Продюсер не знает, куда попадёт сообщение — он шлёт в exchange с routing key. Exchange по bindings раскладывает копии в очереди. Consumer забирает из очереди; после ack сообщение исчезает. Логика доставки живёт **в брокере**.

**Kafka: брокер только хранит, решает consumer**

```text
Producer ──► Topic "orders"
                ├── Partition 0: [m0 m1 m2 m3 ...] ──► Consumer Group A: c1
                ├── Partition 1: [m0 m1 m2 ...]    ──► Consumer Group A: c2
                └── Partition 2: [m0 m1 ...]       ──► Consumer Group B: c1 (свой offset)
                       ↑
              сообщения живут по retention, не удаляются после чтения
```

Продюсер выбирает партицию (по ключу). Сообщения лежат в логе, пока не истечёт retention. Каждая consumer group читает **со своей позиции** (offset) и ни на кого не влияет. Логика доставки — **на стороне потребителя**.

Отсюда два следствия, которые объясняют 80% различий:

1. **В Kafka можно перечитать историю** — offset это позиция в логе, а не «прочитано/удалено».
2. **В RabbitMQ можно гибко маршрутизировать** — exchange и bindings это язык описания «кому какое сообщение».

## Сравнение по ключевым осям

### Порядок и параллелизм

```text
Kafka:                              RabbitMQ:
Partition 0 → [m0 m1 m2 m3]         Queue → [m0 m1 m2 m3 m4]
   один consumer в группе              много consumer'ов,
   порядок строгий                     каждый берёт по мере готовности
Partition 1 → [m0 m1 m2]
   другой consumer                     порядок гарантирован только
   порядок между партициями НЕТ        если consumer один
```

- Kafka: порядок **внутри партиции**, параллелизм ограничен числом партиций. Хотите больше параллелизма — больше партиций (но их нельзя уменьшать).
- RabbitMQ: порядок **внутри очереди при одном consumer'е**. Несколько consumer'ов на очередь = порядок теряется, зато масштабирование «естественное».

### Доставка: push vs pull

```text
RabbitMQ (push):   broker ──► consumer  (с prefetch-лимитом)
Kafka (pull):      consumer ──► broker   (fetch батчами, сам держит темп)
```

Pull в Kafka — это не «медленно», а **контроль темпа**: consumer сам решает, сколько тянуть, и не захлёбывается. Push в RabbitMQ — ниже задержка на отдельном сообщении, но нужен prefetch, чтобы не завалить consumer.

### Что происходит с сообщением после чтения

```text
RabbitMQ:  produce → queue → consume → ack → УДАЛЕНО
Kafka:     produce → log   → consume (offset++) → ЛЕЖИТ до retention
```

Это ключевое различие. В RabbitMQ сообщение — **задача**, её убрали после выполнения. В Kafka сообщение — **запись в журнале**, она остаётся, и её можно перечитать (replay) или прочитать другой группой.

### Гарантии

```text
RabbitMQ:
  publisher confirms  ──┐
  consumer acks       ──┴──► at-least-once (дубли возможны)

Kafka:
  acks=all + min.insync.replicas ──► at-least-once
  + идемпотентный продюсер
  + транзакции                   ──► exactly-once (в пределах Kafka)
```

RabbitMQ надёжен, но exactly-once как first-class не даёт — дубли гасят идемпотентностью в приложении. Kafka умеет EOS, но только в цепочке Kafka→Kafka (для внешней БД всё равно нужен Outbox или идемпотентная запись).

## Сводная таблица

| Критерий | Kafka | RabbitMQ |
|---|---|---|
| Модель | Распределённый лог | Брокер очередей + exchanges |
| Порядок | Внутри партиции | Внутри очереди (при 1 consumer) |
| Маршрутизация | Топик + ключ → партиция | direct / topic / fanout / headers |
| Доставка | Pull | Push |
| После чтения | Живёт по retention | Удаляется после ack |
| Replay | Да, сбросом offset | Нет |
| Параллелизм | ≤ число партиций в группе | Много consumer'ов на очередь |
| Throughput | Очень высокий | Высокий, но ниже |
| Задержка на сообщение | Низкая | Очень низкая |
| Приоритеты / TTL / delayed | Нет из коробки | Есть |
| Exactly-once | Да (в пределах Kafka) | Нет first-class |
| История | Долгая (дни/недели/compaction) | Пока не прочитано |
| Протоколы | Свой бинарный | AMQP, MQTT, STOMP |
| Эксплуатация | Сложнее | Проще на старте |

## Что выбрать — по сценарию

**Kafka**, когда сообщение — это **данные**:

- event sourcing, журнал событий как источник истины;
- несколько независимых потребителей одного потока (fan-out с replay);
- CDC (Debezium + Kafka Connect), интеграция данных;
- stream processing (Kafka Streams, ksqlDB, Flink);
- высокая нагрузка, нужна durability и горизонтальный масштаб;
- аналитика по историческим событиям.

**RabbitMQ**, когда сообщение — это **задача**:

- task queues, распределение работы между воркерами;
- сложная маршрутизация (topic/direct/fanout/headers, bindings);
- приоритеты, per-message TTL, отложенная доставка, DLQ;
- RPC / request-reply;
- IoT/MQTT, умеренные нагрузки, важна простота.

**Ни то, ни другое**, если очередь простая и нагрузка низкая — SQS или Redis Streams будут дешевле в эксплуатации.

---

## Частые ошибки в выборе

- **«Kafka быстрее»** — на throughput да, на latency одного сообщения RabbitMQ часто лучше.
- **«RabbitMQ не масштабируется»** — масштабируется через очереди и consumer'ов; quorum queues дают репликацию.
- **«Kafka — это очередь»** — это лог; очередь — один из паттернов поверх него.
- **«В RabbitMQ нет порядка»** — есть, пока consumer один; с несколькими порядок теряется по определению.
- **«В RabbitMQ есть exactly-once»** — нет; достигается идемпотентностью приложения.

---

## Короткое правило

Спросите себя: **«мне нужно перечитывать историю и обрабатывать её многими способами?»** — Kafka. **«мне нужно прямо сейчас доставить задачу нужному исполнителю?»** — RabbitMQ.
